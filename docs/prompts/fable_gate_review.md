## 0. 배경 (먼저 읽고 시작)

이 저장소는 코인원(수수료 0% 이벤트) KRW 현물 BTC·XRP·ETH 단기 매매 연구·운용 시스템이다. 사용자(소유자)는 초기 자본 약 30만원,
"거래 횟수가 많고, 일부 금액씩 분할 진입하는" 전략을 원한다. 레버리지·공매도 없음(롱 온리 현물).

지금까지 공식 캠페인 31개, 시도 약 178개를 돌렸고 **검증을 통과한 운용 후보는 0개**다.
- 1~5분: 신호 정보는 있으나 1~3bp로 비용(왕복 4bp~)보다 작음 (COST_EATEN)
- 1시간 모멘텀: 개발 구간은 통과한 후보가 2개 있었으나 검증 구간(하락장)에서 탈락
- 분할 매수 그리드(사용자 아이디어): 비용 후 음수
- 합성 시장 보정 결과: 엣지 없는 시장 오탐률 약 0%, 진짜 Sharpe 3 검출률 약 50%, Sharpe 2는 거래 빈도에 따라 0~70%

사용자의 우려: **"관문이 너무 빡빡해서 완벽한 전략만 찾고 있는 것 아닌가?"**
이 작업의 목표는 그 질문에 **증거로** 답하고, 필요하면 **원칙을 지키면서** 조정안을 만드는 것이다.

## 1. 반드시 지킬 원칙 (위반 시 결과 전체가 무효)

1. **골대 옮기기 금지**: 실제 캠페인 결과(어떤 후보가 아깝게 떨어졌는지)를 근거로 기준값을 바꾸지 않는다.
   증거 기준(class ②)의 변경 근거는 **합성 시장 보정 실험**과 **사용자가 명시적으로 선택한 오탐/검출 목표**뿐이다.
   `btc_quant.params.criteria` 의 anti-goalpost 장치를 우회하지 않는다.
2. **소급 적용 금지**: 모든 변경은 다음 캠페인부터(`gate_config_for_campaign`). 이미 검증 구간에서 떨어진 후보는 재평가로 구제할 수 없다(코드로 강제됨 — 유지할 것).
3. **검증 구간(Val)·잠금 구간(lockbox) 세부 수치를 보지 않는다**: `research/reports/human/**`, `research/campaigns/*/pipeline.json`, 원장의 Val/lockbox 파일은 읽지 말 것. 실데이터 연구 결과는 에이전트용 리포트(`research/reports/campaign_*.md`, `cycle*.md`)와 MCP `query_ledger` 로만 본다.
4. **적용은 사용자 승인 후**: 기준값을 직접 바꾸지 말고 `btc_quant.params` 제안(proposal)으로 만든다. 사용자가 채팅으로 승인하면 기존 방식대로 기록한다(`research/param_approvals/` 참고 — 승인 출처를 "user (explicit chat approval <날짜>)"로 남김).
5. **기준의 3분류를 지킨다**(`docs/PARAMS.md`):
   - ① 시장 측정값(비용·체결·데이터 품질): 데이터로 보정, 엄격해지는 방향만 자동
   - ② 증거 기준(유의수준·DSR·PBO·G1~G6 통과선·견고성 임계값): 합성 보정 + 사용자 승인
   - ③ 위험 선호(낙폭 한도·손실 한도·진입 비중): 사용자 가치 판단 — 선택지 표만 제시
6. 테스트는 항상 녹색 유지(`uv run pytest -q`, 현재 약 2,500개). 컨테이너가 예고 없이 재시작될 수 있으니 자주 커밋·푸시.

## 3. 확인할 것 (전수 점검)

### 3.1 관문·설정 전수 표 만들기
`config/params.yaml` 의 모든 항목(현재 약 130개)과 `gates.yaml`·`costs.yaml`·`splits.yaml`·`risk` 관련 값을 하나의 표로 정리:
현재값 / 분류(①②③) / 도입 근거 / 근거가 실측인지·합성인지·임의인지 / 마지막 변경일 / **지금까지 실제로 후보를 떨어뜨린 횟수**(원장의 실패 분류 집계 — 개발 구간 관문만, Val은 결과 코드만).
특히 **근거가 "임의"로 정해진 값**을 표시하라. 예: G1 최소 거래 300회, G3 이웃 중앙값 50%, G4 롤링 60%, G5 DSR 0.95·PBO 0.3, G6 낙폭 20%·MC 낙폭 20%, Val Holm α 0.10·상한 20, 견고성 임계값들(국면 70%, 지연 유지율 0.5, 알파 t 2.0 등), 반감기 365일, 꼬리 위험 임계값.

### 3.2 관문 깔때기 분석 (실데이터, 개발 구간만)
원장의 모든 캠페인에 대해: 각 관문에서 몇 개가 떨어졌나, **첫 탈락 관문** 분포, 비용 전/후 Sharpe 분포, 무작위 기준선 대비 백분위 분포.
목적은 기준을 바꾸는 근거가 아니라 **"어느 관문이 실제로 병목인가"를 아는 것**이다(조정 대상의 우선순위를 정하는 용도).

### 3.3 기준들끼리 중복·과잉 여부
- 같은 위험을 여러 관문이 이중·삼중으로 막고 있지 않은가? (예: 비용 강건성 — G6 스트레스 Sharpe, 견고성 비용 ×1.5/×2, A/B 등급; 국면 의존 — G4 최근 12개월, 견고성 국면 70%, 알파 t)
- 직렬로 연결된 관문들의 **누적 검출률**: 각 관문 통과 확률의 곱이 너무 작아지는지. 각 관문을 하나씩 빼고/완화했을 때 합성 시장의 오탐률·검출률이 어떻게 변하는지 (기여도 분석 — "이 관문이 실제로 가짜를 몇 개 막는가").
- 시도 수 보정(DSR)과 검증 구간 Holm 보정과 잠금 구간 Holm 보정이 **같은 다중검정을 중복 처벌**하고 있지 않은가.

### 3.4 철학 점검 — "완벽한 전략 하나" vs 대안
현재 설계는 "전략 하나가 G0~G8을 모두 통과해야 운용"이다. 다음 대안들을 비교 평가하라:
- **(a) 오탐 허용 목표 상향**: 예) 전체 오탐률 5% → 10%/20% 목표로 보정했을 때 검출률이 얼마나 오르는가 (합성 실험). 자본 30만원 + 리스크 한도 하에서 오탐 1건의 기대 손실 vs 놓친 진짜 엣지의 기회비용을 **의사결정 관점(기대값)**으로 계산해 사용자에게 제시.
- **(b) 단계별 승격**: 개발 구간만 통과한 후보도 "소액 실전/페이퍼 관찰" 단계에 들어갈 수 있게 하고, 실시간 증거로 단계적으로 비중을 늘리는 구조 (예: 잠정 등급 → 페이퍼 → 자본 10% → 30% …). 이때 필요한 안전장치.
- **(c) 슬리브 포트폴리오**: 개별 전략 기준을 다소 낮추고 대신 포트폴리오 전체(여러 약한 전략·여러 코인)를 검증하는 구조. 다중검정·상관 처리 방법 포함.
- **(d) 위험 관리형 보유**(사용자가 함께 진행하기로 결정): 3코인 보유 + 추세 이탈 시 현금 전환 + 분할 적립. 이 경우 관문의 기준점을 "현금 대비 Sharpe>0"이 아니라 **"보유 대비 위험 조정 성과"**로 볼지 — 그에 맞는 관문 설계안.

### 3.5 측정값(class ①) 점검
- 비용: 코인원 BTC 실측 왕복 약 1bp vs 보수 가정 4bp, XRP/ETH 잠정치(15분 표본). 지금까지 쌓인 실시간 수집 데이터(`data/raw/exchange=*/symbol=*/{trades,orderbook}/`)로 재보정 가능한지 — 가능하면 `python -m btc_quant.params calibrate` 경로로 보정하고 결과 보고(느슨해지는 방향은 제안만).
- 지정가 체결 규칙(1틱 관통)과 역선택 측정치가 충분한 표본인지.
- 데이터 품질 임계값(오체결 k, 빈 봉 처리)이 코인별로 적절한지.

## 4. 수행할 분석 (합성 보정 실험)

`src/btc_quant/research/calibration_study.py` 와 `btc_quant.params.criteria.propose_criterion` 을 사용한다. 실험 설계:
1. **시장 종류**: 기존 표준(무작위 보행·GARCH·시간대 계절성) + 국면 전환 시장 + 3코인 시장(공통 요인 + 개별 요인) + 거래 빈도별(하루 0.2 / 1 / 5 / 15회) 심은 엣지.
2. **엣지 강도**: 진짜 비용 후 Sharpe 0 / 0.5 / 1 / 1.5 / 2 / 3.
3. **변형**: 3.1에서 "임의"로 표시된 기준 각각을 여러 값으로, 그리고 **기준 묶음(패키지)** 2~3개 — 예) "현재", "중도(오탐 10% 목표)", "적극(오탐 20% 목표)".
4. **측정**: 전체 오탐률·하락장 검증 구간에서의 오탐률·엣지 강도×거래 빈도별 검출률·관문별 첫 탈락 분포, 모두 Wilson 신뢰구간. 원장에 시도가 누적된 상황(10~20개 캠페인)도 포함.
5. 같은 시드로 변형 간 쌍대 비교. 실행 시간이 길면 하위 에이전트로 병렬화(시장 수를 쪼개 실행 후 합침).

## 6. 작업 환경 메모

- Python 3.13, `uv run ...`. 엔진은 numba. 전체 테스트 약 5~8분.
